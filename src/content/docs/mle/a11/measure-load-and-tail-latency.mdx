A load experiment needs an offered rate, request mix and a time window. A closed-loop benchmark starts new work only as previous requests finish, which can reduce the offered pressure when a service slows. An open-loop pattern can better expose how a queue behaves under an external arrival rate. Configure either workload carefully and report which was used.

<Term id="goodput" cap /> can count successes within a latency objective per second, rather than counting every request the system accepted. A server with high raw throughput can still miss the objective. Show failures and slow successes as well as p95, and say whether latency percentiles are calculated only for completed calls.

This exercise uses nearest-rank p95 over successes and treats timeouts as missing latencies. It also reports on-time success count. Use the measurement window in seconds to convert that count to goodput. A tiny test gives a coarse tail estimate even when the calculation is correct.

## Worked example

The example separates the tail from failures and on-time completions.

```python
def load_summary(latencies, target_ms):
    from math import ceil
    succeeded = sorted(value for value in latencies if value is not None)
    p95 = succeeded[ceil(0.95 * len(succeeded)) - 1] if succeeded else None
    return {"attempted":len(latencies), "failed":len(latencies)-len(succeeded),
            "p95_success_ms":p95, "on_time":sum(value <= target_ms for value in succeeded)}

print(load_summary([15, None, 60, 20], 20))
```

```text title="Output"
{'attempted': 4, 'failed': 1, 'p95_success_ms': 60, 'on_time': 2}
```

Compare tail latency and goodput together before increasing offered traffic.
