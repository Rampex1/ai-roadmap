With vectors normalised as in [lesson 2](/llm/c4/similarity-metrics/), search is simple: score the query
against every stored vector, keep the best $k$. This is **exact** (or brute-force, flat) search. It is the
reference every faster index is measured against, and for small corpora it is often all you need.

## What brute force costs

Store $n$ vectors of dimension $d$ as the rows of a matrix $X$ ($n \times d$). For a unit query
$\mathbf{q}$, all $n$ scores come from one matrix-vector product, $\mathbf{s} = X\mathbf{q}$. Each score
reads $d$ coordinate pairs, so the work per query is proportional to $n \cdot d$, written
$O(n \cdot d)$. Doubling the corpus or the dimension doubles the work.

Memory is just as direct. A float32 number takes 4 bytes, so the matrix needs

$$
\text{bytes} = n \times d \times 4
$$

**Worked example.** One million chunks embedded at $d = 768$:
$1{,}000{,}000 \times 768 \times 4 = 3{,}072{,}000{,}000$ bytes $\approx 3.07$ GB (decimal). On an 8 GB
laptop that is most of the free memory, before the encoder, the application and the operating system.
At $d = 384$ the same corpus takes 1.536 GB. Each query must also read all of those bytes, so its time is
largely set by memory bandwidth: expect tens of milliseconds per query at this size on a laptop, and
proportionally less for smaller corpora. For 10,000 chunks it is a fraction of a millisecond, and an
index would be wasted effort.

Picking the top $k$ does not need a full sort. A partial selection such as numpy's `argpartition`, or a
heap of size $k$, finds the best $k$ in time proportional to $n$; only those $k$ then need sorting.

## Filter first, then take top-k

Real searches carry conditions: only billing articles, only documents this user may read, only notes
newer than last year. A <Term id="metadata-filter" /> decides which records are **eligible**; the score
only orders eligible records.

The order of the two steps matters. **Post-filtering** takes the global top $k$ and then drops ineligible
results, which can leave fewer than $k$ results, or none, even when good eligible documents exist.
**Pre-filtering** restricts to eligible records first, then takes the top $k$ among them.

```python
import numpy as np

ids = np.array(["a", "b", "c", "d", "e"])
cats = np.array(["billing", "tech", "billing", "billing", "tech"])
X = np.array([[0.6, 0.8], [1.0, 0.0], [0.8, 0.6], [0.8, 0.6], [0.0, 1.0]])  # unit rows
q = np.array([1.0, 0.0])

scores = X @ q                       # n dot products in one matrix-vector product
print(scores)

# Post-filter: take the global top 2, then drop ineligible ones.
top2 = np.argsort(-scores, kind="stable")[:2]
print([str(ids[i]) for i in top2 if cats[i] == "billing"])

# Pre-filter: restrict to eligible rows, then take the top 2 with ties broken by ID.
eligible = np.flatnonzero(cats == "billing")
best = sorted(eligible, key=lambda i: (-scores[i], ids[i]))[:2]
print([str(ids[i]) for i in best])
```

```text title="Output"
[0.6 1.  0.8 0.8 0. ]
['c']
['c', 'd']
```

The tech article `b` took a slot in the global top 2, so post-filtering returned one billing result
although two equally good ones exist. Vector databases implement filtering in different ways, and some
approximate indexes filter during or after the search; check what yours does, and test with a
restrictive filter.

:::caution[Eligibility is an access-control decision]
When the filter enforces permissions, it must come from trusted application data (the logged-in user's
workspace, say), never from text a user or a model wrote. A document that should not be visible must not
be scored and then hidden; it must never enter the candidate set.
:::

## Ties and reproducibility

`c` and `d` have the same vector, so they score exactly 0.8. Which comes first? Without a rule, the
answer depends on storage order, threading or the library version, and a test that passed yesterday
fails today. The lesson's convention is to sort by the key **(−score, id)**: highest score first, then
ascending ID. Every run, and every implementation that follows the rule, returns the same list.

Ties are not exotic. Duplicated documents, boilerplate chunks ("Contact support for help") and quantised
scores all produce them. A deterministic exact baseline is what lets you say "the approximate index
missed this document" rather than "the order happened to change".

Two more edge cases belong in the contract: fewer eligible records than $k$ (return them all, not an
error) and $k = 0$ (return an empty list). A negative $k$ is a bug in the caller, so raise an error.
